# Chapter 1. Project Overview

## 1.1 Introduction

Shared cloud and AI clusters run jobs from many users on a common pool of machines. Before a job is admitted, its owner states how much CPU and memory it requires, and the scheduler reserves that amount for the job's lifetime. The owner must make this estimate before the job has run, and the costs of a wrong estimate are asymmetric. A request that is too low can cause CPU throttling, out-of-memory termination or eviction, and the job may have to be rerun; a request that is too high only reserves capacity that no other job can use. Users therefore tend to request more than their jobs consume, and trace studies of production clusters report large and persistent gaps between allocated and used resources [Le 2020].

Production traces record both what jobs requested and what they used, and many cluster jobs recur: the same workload is submitted repeatedly, for example as a scheduled pipeline or a periodically retrained model. Resource Central showed that the behavior of production workloads is consistent enough across executions for historical data to support resource prediction [Cortez 2017], and Accordia showed that recurring batch workloads can be optimized using information from their earlier executions [Liu 2023]. For a recurring workload, the usage of earlier runs is therefore direct evidence about the next run.

TraceAdvisor uses this evidence to recommend CPU and memory for the next run of a recurring workload before it is submitted. It derives each recommendation only from runs that had completed before the new run started, and it evaluates the recommendations by replaying production traces in time order. Because it operates offline and only advises on the request, it requires no change to the scheduler and no additional executions of the workload.

## 1.2 Problem Statement

Existing approaches to the gap between requested and used resources act at different points of a job's life. Flex reclaims the gap at runtime through oversubscription [Le 2020], which operates after submission and gives the user no guidance on what to request. QoS-based pricing and scheduling addresses the problem on the provider's side through prices and scheduling policies [Sandholm 2015], not through an estimate of the job's needs. Configuration recommenders such as Accordia use the history of recurring workloads, but they search over cloud configurations using online experiments with Gaussian-process methods [Liu 2023], which requires running the workload on candidate configurations.

The problem addressed in this project is therefore to recommend, before a recurring job is submitted, how much CPU and memory it should request, using only the trace history available at that time, without modifying the scheduler and without running the job on trial configurations. A useful recommendation must balance two failure modes that cannot be priced against each other for a public trace: under-provisioning, which risks job failure, and over-provisioning, which wastes capacity. A method for this problem must also be evaluated honestly: the evaluation must use only information available before each run, keep the data used for decisions separate from the data used to report results, and report both failure modes rather than a single combined score.

## 1.3 Literature Review

### 1.3.1 Over-Provisioning and Resource Allocation

Trace studies of large clusters consistently find that users request more resources than their jobs use. Flex analyzed production cluster traces, measured substantial differences between requested and actual usage, and proposed a runtime manager that reclaims part of the difference through oversubscription [Le 2020]. An analysis of Google ClusterData 2019 related job failures to user behavior and to inefficient resource management [Chowdhury 2023], and a data-driven case study of Azure workloads found widespread underutilization of provisioned resources [Everman 2022].

The causes of over-provisioning are partly economic. QoS-based pricing and scheduling explains how uncertainty about resource needs leads users to over-provision to avoid job failures or performance degradation [Sandholm 2015]. Although that work addresses provider-side pricing, it locates the source of inefficiency in the decision made before submission. Together, these studies show that the gap between requested and used resources is large, persistent and measurable from traces, and that it originates in the request itself.

### 1.3.2 Datasets and Trace Foundations

Public production traces make it possible to study resource requests and usage at scale. Resource Central, a study of virtual machine workloads on Microsoft Azure, showed that historical workload behavior can predict future behavior well enough to inform resource management [Cortez 2017]. Its trace and other Azure public datasets [Azure datasets] provide virtual machine and service-level data, and the Philly study of a multi-tenant GPU cluster identified GPU underutilization and scheduling challenges in deep learning training workloads [Jeon 2019]. Splitwise [Splitwise 2024] and ModServe [ModServe 2025] showed that AI inference workloads have different resource demands across processing stages.

TraceAdvisor requires a trace that records, for individual jobs, a resource request, the usage of each run and a way of recognizing runs of the same workload. Google ClusterData 2019 [Wilkes 2019] records job and task lifecycle events, resource requests and sampled resource usage from Google's Borg clusters; this project uses a publicly available 31-day sample of it [Kaggle subset], from which recurring workloads and their runs are reconstructed. The Alibaba GPU Cluster Trace 2020 [Alibaba 2020] records machine learning jobs from Alibaba's Platform for Artificial Intelligence, whose analysis reported low GPU utilization, varied workload demands and CPU bottlenecks [Weng 2022]. It is the only one of the Alibaba traces examined in this project that provides both an official recurrence tag and a memory peak in the same unit as the memory request. The Azure traces were used for earlier baseline experiments but describe virtual machines or service-level demand rather than recurring jobs with per-job requests, so they could not be used to evaluate next-run recommendations (Section 3.3.3).

### 1.3.3 Existing Resource Recommendation Approaches

Approaches that use historical data to improve resource decisions fall into three groups. The first uses execution traces to optimize batch processing in public clouds; Scheinert et al. examined the potential of such traces for workload optimization [Scheinert 2021]. The second recommends cloud configurations. CherryPick searches for the best configuration of a big data analytics job using Bayesian optimization [Alipourfard 2017], Accordia specializes this search to recurring batch workloads [Liu 2023], and Scavenger extends configuration optimization to ML training [Tyagi 2023]. These methods choose among configurations by running the workload on some of them, whereas TraceAdvisor recommends resource amounts from completed runs without additional executions.

The third group uses usage percentiles to size resources. Resource Central used historical Azure workload data to inform resource management decisions [Cortez 2017], and work on virtual machine downsizing on Azure used percentile-based CPU estimates to decide how far a virtual machine could be reduced [Huang 2023]. TailGuard showed the importance of high-percentile objectives, such as the 95th and 99th percentiles, for controlling rare but costly events [Wang 2025]. Percentiles suit resource sizing because a recommendation at the p-th percentile of past usage states directly the share of past runs it would have covered. These studies support the use of historical percentiles as a safeguard against under-provisioning, and they leave open how a learned prediction should be combined with such a safeguard.

### 1.3.4 Research Gap

The literature establishes three findings. Over-provisioning is widespread and measurable in production traces [Le 2020, Everman 2022]; the history of recurring workloads carries information about their future behavior [Cortez 2017, Liu 2023]; and high percentiles of past usage are an established basis for safe sizing [Huang 2023, Wang 2025]. The existing systems, however, act at runtime, require scheduler integration, rely on online experiments over configurations or address the provider's side of the problem. None of the reviewed work recommends CPU and memory for the next run of a recurring job before submission from trace history alone, combines a learned prediction with a percentile safeguard so that the prediction can only add capacity, and evaluates the result by time-ordered replay with a test period that is scored once after every decision has been fixed. TraceAdvisor addresses this gap, and applies the method to two traces with different workloads and measurements to test whether its conclusions depend on one of them.

## 1.4 Project Objectives and Scope

The objective of TraceAdvisor is to build and evaluate an offline, trace-driven system that recommends CPU and memory for the next run of a recurring cluster workload before it is submitted, reducing over-provisioning while keeping the risk of under-provisioning low. The objective is pursued through four aims:

1. Transform each trace into a common representation in which every evaluated run of a recurring workload has its request, its usage and its history of earlier completed runs, with the meaning and unit of every value recorded.
2. Compare seven recommendation policies: the user's request; the mean and the 90th, 95th and 99th percentiles of earlier usage; an ML prediction; and a Hybrid policy that takes the larger of the ML prediction and a historical percentile.
3. Evaluate the policies by replaying each trace in time order, measuring violation rate, shortfall, waste and utilization separately for CPU and memory, with all choices made on a validation period and the test period scored once.
4. Apply the same method to a second trace with different workloads and measurements, to test whether the conclusions depend on one trace.

The scope is limited to two traces. Google ClusterData 2019 is the primary dataset, on which the method was developed; its evaluation unit is a reconstructed occurrence of a recurring workload, and CPU and memory are both peak usage in normalized units. The Alibaba GPU Cluster Trace 2020 is the second dataset; its evaluation unit is one role within one job, with values per instance, memory is a lifetime peak in gigabytes, and CPU is available only as a lifetime average, so its CPU results describe average-usage sizing rather than peak safety. The two datasets are processed by separate pipelines and their results are not compared numerically. Recommendations cover CPU and memory, the two resources recorded in both traces; GPU sizing is outside the scope. TraceAdvisor is an advisory system evaluated offline: it does not modify a scheduler, does not execute workloads and does not measure application performance.

## 1.5 Project Contributions

The project makes four contributions.

1. A shared data model for heterogeneous traces. Each trace is mapped by a dataset-specific adapter into a canonical schema that records the scope, unit and meaning of every resource value, and a capability profile per dataset states which resources and metrics may be reported. From the canonical data onward, histories, targets, recommendations and evaluation use the same code for both datasets, so adding a trace requires a new adapter rather than a new pipeline.
2. A recommendation method that combines a learned prediction with a historical safeguard. The Hybrid policy takes the larger of an ML prediction and a historical percentile, so it never recommends less than its safeguard; the prediction adds capacity only where the model expects the next run to exceed what the history suggests.
3. A leakage-controlled replay evaluation. Recommendations use only runs that had completed before each run started, selection is made on a validation period, and every decision is written to a decision manifest with the checksums of its inputs and the code version before the test period is scored once. A second test run is refused, and a known limitation of the Google targets is measured and reported.
4. Results on two production traces. On both Google ClusterData 2019 and the Alibaba GPU Cluster Trace 2020, Hybrid had fewer violations than its historical safeguard at almost the same waste, while the ML prediction alone was the least wasteful policy but under-provisioned between one run in three and one run in two. Historical percentiles traded violations against waste, and the user's request was a poor sizing signal on both traces, too low on Google and generous for memory on Alibaba.
